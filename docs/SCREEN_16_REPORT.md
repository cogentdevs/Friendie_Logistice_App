# Screen 16 - Premium Register

## Access and UI

Sign In -> Register opens src/features/auth/screens/RegisterScreen.tsx in the existing AuthNavigator. Both back and the Sign In footer return to Login. No additional navigation container, tabs or Expo dependency was added.

The screen reuses logo1 through BrandLogo, centralized colors, AppInput, GradientButton, KeyboardScreen and ScreenContainer. It includes a white safe-area layout, burgundy CTA, full name/email/phone/password/confirmation fields, independently controlled password visibility, live password indicators, consent checkbox, inline error announcements and a scrolling keyboard-safe form. Android already uses adjustResize. Native iOS runtime testing is not available on this Windows host.

## Validation and privacy

React Hook Form and Zod validate trimmed full name, normalized email, the selected country's supported mobile-number format, a local minimum of eight password characters, matching confirmation and consent. Passwords are not trimmed. Supported formats are Pakistan, UAE, Saudi Arabia, UK and US; the selector explicitly labels this limited coverage. National and matching international formats normalize to an international number. Format validation does not verify number ownership, assignment or all possible national number types.

No registration credentials or draft are persisted or logged. Mutation retries are disabled, submissions are guarded and controls disabled while pending. Mutation state is reset after completion with zero cache retention. Registration never creates a fake session or bypasses verification.

## Backend and legal dependencies

The repository contains proposed login/logout/user endpoints but no verified registration endpoint, payload names, password policy or success/verification response. registrationService is therefore an explicitly unavailable integration boundary: it validates a typed domain input and returns an honest error without making a network request. prepareRegistration is NOT a claimed Laravel request contract. No registration endpoint or token response shape was invented.

Before enabling real registration, confirm the endpoint and actual field names, server password policy, consent requirements and response variants. Wire this boundary to the existing API client; use existing Keychain/session hydration only for an explicitly confirmed authenticated result, and implement a verified verification-pending flow when required. Success, automatic authentication and verification navigation are pending this contract.

The form can present recognized inline field errors, including email/phone duplicates, and network, server and rate-limit failures. Tests simulate these errors at the service boundary; these are not live backend validation results.

TERMS_URL and PRIVACY_URL are new optional public configuration values generated by configure-env.cjs. Links open configured HTTPS documents through Linking; missing or failed documents show inline feedback. No legal URLs were invented. Real account creation must remain unavailable until the actual policies and backend are supplied. Existing Sign In UI preview remains accessible without credentials.
