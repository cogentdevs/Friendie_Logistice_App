# Get Categories API integration

## Verified contract

Public GET `/api/v1/categories` (centralized base URL already includes `/api/v1`).
Optional `search`: trimmed nullable string, maximum 100 characters. Complete,
unpaginated reference list. No request body or Bearer token.

HTTP 200:
```json
{"success":true,"message":"Categories retrieved successfully.","data":{"items":[{"id":1,"name":"Food Items","image_url":null}]}}
```

Verified read-only against Laravel `routes/api.php`, API V1 CategoryController,
ReferenceDataQuery, PublicData::category/image, and ApiResponse. The controller
selects only isActive=1 records. Ordering is backend name then ID (search additionally
ranks exact/prefix matches). No parent/status fields are returned to the client.
`image_url` is an absolute HTTP(S) URL generated by the backend's trusted public
media configuration, or null for unavailable images. No client URL construction.
Empty result is `data.items: []`. Shared API error normalization remains unchanged.

## Frontend wiring

- `services/api/endpoints.ts`: verified `/categories` path.
- `features/home/services/categoriesService.ts`: typed, validated public Axios GET,
  AbortSignal, optional search, safe actionable error copy. Normalizes numeric IDs
  to strings for existing category/card/filter contracts; names, order and IDs are
  otherwise unchanged. Null images use the existing generic Package icon.
- `features/home/services/homeService.ts`: normal category reads use the real service.
- `features/home/hooks/useHomeData.ts`: existing React Query cache, public key
  `['home','categories','api']`; 60-second freshness, focus enabled, automatic retry
  disabled. Request cancellation is forwarded. No auth owner in the key. Existing
  retry/pull-to-refresh provides one error Toast for a failed user request; initial
  failures stay inline, no success Toasts. Concurrent retries share one promise;
  unmounted callers cannot emit late Toasts.
- HomeScreen sample-content caption no longer labels API categories as sample data.
  No card/component styles, icons, dimensions, section order or navigation changed.

## Static testing and listings limitation

Only the explicit native STATIC_TESTING build, with existing fixtures enabled,
retains the original sample categories and sample identities. Its separate cache
key is `['home','categories','static-testing']`. Debug alone uses the real API;
normal release uses the real API. Authentication/preview state never selects the
category source. API failures never silently fall back to fixtures. Existing
Listings/Latest Ads/Popular Locations static configuration is unchanged.

Category taps, View All selection and Home search retain backend ID as a string in
`SearchFilters.category` and open existing public Results. Static listings currently
filter by their fixture category name, not backend category ID. Therefore a real
category ID has no matching fixture listings and truthfully yields an empty result.
No name/ID substitution or fabricated match is made. Future Listings integration
must map this real ID to documented `category_id` using the actual Listings DTO.

Existing logout may clear the query cache as part of private-state cleanup. This
public query has no auth gate and loads again on Home; it never switches to fixtures
or requires Login after logout. Logout/session architecture was not changed.

## Verification

category, Food Items (ID 1), and its absolute image URL. Matching search and no-match
empty search verified. Opt-in test `categories.live.test.ts` uses the production
service and centralized Axios with Node HTTP adapter, and checks real 422 search
validation. Run with FRIENDIE_RUN_CATEGORIES_LIVE=true; it does not write backend data.

Adapter tests cover public guest/member headers, ID/name/image ordering, null image,
empty response, malformed envelopes, HTTP 401/403/404/429/500, network/timeout, abort,
and explicit static-testing isolation. Home tests cover real categories, ID-based
public navigation, query reuse across auth changes, loading/empty and retry Toasts.

No phone installation or visual testing was performed. Physical devices require a
reachable configured API/media host; localhost refers to the phone unless an
existing development ADB reverse is used. No Android network security or environment
configuration was changed. Future production backend/media availability remains an
operational requirement.
